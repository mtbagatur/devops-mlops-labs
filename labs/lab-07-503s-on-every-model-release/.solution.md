# Lab 07 — Hidden solution (spoiler)

## Root cause
- The readiness probe checks `/health`. On this server (as on vLLM) `/health` answers 200 as soon as the HTTP process is up, about 20 seconds before the weights are loaded. `/v1/models` and `/v1/completions` return 503 until loading finishes.
- So a new pod is marked Ready about 5 seconds after start, gets added to the Service endpoints, and receives real traffic while it still answers 503.
- `maxUnavailable: 1` then terminates an old, fully loaded pod as soon as the new one is "Ready". For most of the rollout, 1–2 of the 3 endpoints are pods that cannot serve, which matches the error ratio seen in env/traffic.sh (about 15% over a 2-minute window).
- `kubectl rollout status` only waits for Ready, so the pipeline reports success. The 503s "fix themselves" once all pods finish loading.

## Reference sequence
1. `kubectl get deploy llm-gateway -n support-ai -o jsonpath='{.spec.template.spec.containers[0].readinessProbe}'` shows `/health`.
2. On a fresh pod (`kubectl rollout restart`, then quickly): `kubectl exec <new-pod> -- python -c "import urllib.request as u; ..."` against `/health` (200) and `/v1/models` (503). Or port-forward and curl both.
3. `kubectl get endpoints llm-gateway -n support-ai -w` during a rollout: the new pod IP joins within seconds.
4. `kubectl logs <new-pod>` shows 503 lines for `/v1/completions` and "model … loaded in 20s" only later.
5. `bash env/traffic.sh` reproduces `failed>0`.

## Mitigation (task 2)
- Simplest: `kubectl rollout pause deploy/llm-gateway`, so no more old pods are replaced. The pods that are already Ready finish loading within ~20s. Then `kubectl rollout resume`. Undo: don't forget the `resume`; that was a weak area in lab 02.
- Alternative: `kubectl rollout undo` costs another round of loading; it's worse unless v2 itself is broken.
- Don't scale down, and don't delete pods.

## Fix (tasks 3–4)
- `readinessProbe.httpGet.path: /v1/models` (any endpoint that needs the loaded model works).
- `livenessProbe` stays on `/health` (process alive). Putting liveness on `/v1/models` makes the kubelet kill pods that are still loading. With a slow model this is a restart loop.
- For long or unpredictable load times, add a `startupProbe` (e.g. on `/v1/models` with `failureThreshold * periodSeconds` > the worst load time). Liveness only starts after the startup probe succeeds.
- Optional, and good: `maxUnavailable: 0`, `maxSurge: 1`. Full capacity stays during the rollout, at the cost of one extra pod's resources.
- Apply with `kubectl apply -n support-ai -f env/manifests`, then check with `bash env/traffic.sh` (failed=0).
- The `preStop: sleep 5` in the manifest is already right. It gives kube-proxy time to remove the endpoint before the old process stops.

## Prevention (task 5)
- Pipeline gate: after `rollout status`, a smoke test that calls `/v1/models` and checks that the expected model id is listed, not just `/health`.
- Better: a release test under synthetic traffic in staging (like `env/traffic.sh`) that fails on any 5xx.
- Policy: for model servers, readiness must depend on the model being loaded. Add it to the deployment checklist or enforce it with a policy (e.g. Kyverno: readiness path must not equal liveness path for `app.kubernetes.io/component=inference`).
- Alerting: a separate "5xx during deploy" alert, so "fixes itself" errors are still counted against the SLO.
