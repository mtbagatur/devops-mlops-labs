# Lab 03 — Hidden solution (spoiler)

## Root cause
- Until this release the Secret `fraud-api-secrets` was created by hand (runbook step) and held a valid key.
- Commit 9c41e2a made the chart own the Secret. `values.yaml` has `mlModelApiKey: ""` and the pipeline never passes the key, so `helm upgrade` overwrote the valid Secret with an empty string (Helm 3 three-way merge adopts and patches it).
- Azure DevOps secret variables are not exposed as environment variables or Helm values automatically; they must be mapped explicitly. `$(ML_MODEL_API_KEY)` appears nowhere in the HelmDeploy arguments.
- Old pods still work only because env vars are resolved at container start. **Any restart of an old pod (OOM, node drain, eviction) will now crash it too** — production is one restart away from a full outage.

## Simulated environment facts (keep consistent)
- `kubectl get secret fraud-api-secrets -n fraud-prod -o jsonpath='{.data.ml-model-api-key}' | wc -c` → `0`.
- `kubectl get secret ... -o jsonpath='{.metadata.managedFields[*].manager}'` → `kubectl-create`, `helm`; annotations `meta.helm.sh/release-name: fraud-api`.
- `kubectl get secret ... -o jsonpath='{.metadata.creationTimestamp}'` → 7 months ago (created by hand, adopted by Helm).
- `helm history fraud-api -n fraud-prod` → rev 41 deployed (today), rev 40 superseded.
- `helm get values fraud-api -n fraud-prod` → only `image.tag` user-supplied; `--all` shows `secrets.mlModelApiKey: ""`.
- `helm get manifest fraud-api -n fraud-prod --revision 40 | grep -c fraud-api-secrets` → 0 (Secret not in chart before).

## Reference sequence
1. `kubectl logs --previous`, `kubectl describe pod` → crash reason, env source.
2. `kubectl get deploy -o yaml | grep -A5 secretKeyRef`, `kubectl get rs` → old vs new RS.
3. Secret key exists: `kubectl get secret -o jsonpath='{.data}' | jq 'keys'` (keys only); empty check via `wc -c` / `jq '.data["ml-model-api-key"] | length'` — never decode.
4. Ownership: annotations/labels/managedFields; `helm get manifest`, `helm history`, `helm get values --all` (careful: this prints values — acceptable here because it is empty; never on a release that contains secrets).
5. Pipeline: secret vars need explicit mapping; HelmDeploy args don't reference it.
6. Repair: restore value from the source of truth (Key Vault) straight into the Secret without printing: `az keyvault secret show ... --query value -o tsv | kubectl create secret generic ... --from-file=ml-model-api-key=/dev/stdin --dry-run=client -o yaml | kubectl apply -f -`. CrashLoopBackOff pods pick it up on their next restart; old RS untouched. Then immediately fix the chart before any further `helm upgrade` would blank it again.
7. Verify: new pods Ready, rollout complete, old RS → 0, length check > 0.

## Redesign
- Chart must not carry secret values: `existingSecret` value, Secret created by External Secrets Operator or Secrets Store CSI driver from Azure Key Vault (workload identity).
- If Helm must render it: `{{ required "mlModelApiKey is required" .Values.secrets.mlModelApiKey }}` so empty fails the release; `helm.sh/resource-policy: keep`.
- `--set` secrets end up in the Helm release Secret `sh.helm.release.v1.fraud-api.v41` (base64+gzip, readable by anyone with Secret read in the namespace), in `helm get values` output, in agent logs if not masked, and in process args.
- Pipeline gate: `helm diff upgrade` / `helm template` check in PR; deployment validation with automatic rollback.
